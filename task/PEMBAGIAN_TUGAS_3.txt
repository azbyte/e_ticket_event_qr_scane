BAGIAN 1 – INFORMASI DAN KONDISI PROYEK
--------------------------------------------------------------------------------

1.1 Kondisi proyek
- Pengembangan saat ini berfokus pada frontend Flutter di folder `apps`.
- Repository juga memiliki `backend/` dan sebagian service Flutter dapat
  melakukan request HTTP; jangan gunakan jalur tersebut untuk tugas ini.
  Ruang lingkup saat ini hanya tampilan/prototipe UI Flutter di `apps` dengan
  data dummy lokal. Backend dan integrasinya dikerjakan pada tahap berikutnya.
- Semua interaksi yang ditampilkan (form, filter, status, CRUD, moderasi,
  pembayaran, scanner/check-in) hanya simulasi lokal untuk demonstrasi; tidak
  melakukan request jaringan, menyimpan data sungguhan, atau menjalankan proses
  bisnis nyata. Data boleh berupa fixture statis atau state sementara.
- Model, provider, service, konstanta, dan route di `apps/lib` termasuk scope
  hanya jika tercantum sebagai file milik developer pada Bagian 4; file shared
  yang tidak tercantum sebagai milik developer harus diperlakukan read-only.
- Provider/service/mock adapter hanya dibuat atau diubah jika diperlukan oleh
  tampilan dan hanya boleh mengelola data dummy lokal; tidak membuat integrasi
  backend atau persistence. Pertahankan state loading/error/empty/success untuk
  demonstrasi UI.

1.2 Batasan pengerjaan
- Implementasi tugas ini diizinkan hanya pada frontend `apps` dan file yang
  developer miliki sesuai Bagian 4, termasuk test domain masing-masing.
- Fokus implementasi adalah tampilan dan interaksi demonstratif berbasis data
  dummy. Tidak mengimplementasikan backend, endpoint/API, HTTP, database,
  persistence, pembayaran/auth/check-in nyata, atau logika bisnis produksi.
- Jangan mengubah `backend/`, migration/database, endpoint/API, konfigurasi
  global, dependency, generated files, atau role schema sebagai bagian dari
  prototype ini.
- Jangan mengubah PRD atau dokumen pembagian ini selama implementasi fitur.
  Perubahan biasa pada file milik developer lain harus diminta kepada
  pemiliknya. Jika lebih dari satu developer mengedit path file yang sama,
  hentikan edit paralel dan serahkan rekonsiliasi file tersebut kepada
  Developer 1 Tahap 2; ini pengecualian terbatas dari aturan kepemilikan file.
- Semua pembayaran, auth, laporan, moderasi, scanner, dan check-in di tahap ini
  adalah simulasi UI/fixture; jangan mengklaim sebagai transaksi atau keamanan
  server yang sesungguhnya.

1.3 Tujuan akhir dokumen
- Menyusun pembagian tugas yang jelas untuk 3 developer sehingga seluruh fitur
  tampilan Role Organizer dan Role Admin sesuai `prd.md` tersedia sebagai
  prototipe UI di frontend `apps`, memakai data dummy saja.
- Setiap pekerjaan memiliki satu developer penanggung jawab (OWNER), tanpa
  tanggung jawab tumpang tindih antara Developer 2 dan Developer 3.
- Kontrak integrasi antardeveloper jelas terdefinisi.
- Dokumen dapat langsung digunakan sebagai pedoman pengerjaan tanpa analisis
  ulang dari awal.

BAGIAN 2 – ANALISIS KEBUTUHAN PRD

2.1 Kebutuhan Role Organizer (berdasarkan prd.md bagian 3-6, 11, FR-09 s.d. FR-79)

a) Manajemen Event (FR-09, FR-10, FR-11)
   - Owner dapat membuat dan mengedit event.
   - Event baru berstatus DRAFT.
   - Owner dapat mengajukan event untuk moderasi (DRAFT -> PENDING_REVIEW).
   - Owner dapat mengajukan ulang setelah revisi/penolakan.

b) Kategori Tiket dan Kuota (FR-17, FR-18, FR-19, FR-20, FR-21, FR-22)
   - Owner dapat membuat beberapa TicketType (nama, deskripsi, harga, kuota,
     periode penjualan, status).
   - Sistem membatasi pemesanan berdasarkan kuota.
   - Beberapa tiket dalam satu Order.
   - Perubahan harga tidak mengubah Order lama.

c) Dashboard Organizer (FR-66 s.d. FR-73)
   - Statistik event milik Organizer.
   - Daftar peserta, Order, Payment, check-in.
   - Pencarian dan filter peserta.
   - Pencatatan metode registrasi mandiri/dibantu.
   - Laporan penjualan dan kehadiran.
   - Ekspor CSV sesuai prioritas dan hak paket.
   - Aktivitas event.
   - Staff hanya melihat menu/data sesuai permission.

d) Manajemen Staff (FR-60 s.d. FR-65)
   - Undang Staff melalui email/tautan aman dengan masa berlaku.
   - Staff menerima undangan.
   - Owner mengatur permission per Staff.
   - Owner mencabut akses.
   - Staff hanya mengakses event yang ditugaskan (bukan role global).

e) Scanner dan Check-in (FR-50 s.d. FR-59)
   - Owner membuka scanner pada event miliknya.
   - Staff dengan permission scanner.
   - Simulasi scan/check-in, hasil valid/digunakan/tidak valid/salah event/
     dibatalkan/gangguan jaringan.
   - Mode offline terbatas.

f) Registrasi Dibantu (FR-30, FR-31, FR-32, FR-33)
   - Owner membantu registrasi peserta.
   - Staff dengan permission ASSIST_REGISTRATION membantu registrasi.
   - Kedua metode menggunakan alur Order/Payment/Ticket yang sama (disimulasi).

g) Paket dan Langganan Organizer (FR-77, FR-78, FR-79)
   - Organizer melihat paket dan langganan sendiri.
   - Backend memeriksa batas fitur paket (disimulasi di frontend).
   - Riwayat perubahan paket/langganan disimpan.

h) Dukungan Organizer (FR-95, FR-96)
   - Organizer mengirim keluhan terkait platform.
   - Sistem membuat nomor laporan dan token status aman.

i) Profil dan Notifikasi
   - Halaman profil Organizer, edit profil, logout.
   - Daftar notifikasi.

2.2 Kebutuhan Role Admin (berdasarkan prd.md bagian 6, 11, FR-74 s.d. FR-106)

a) Dashboard Bisnis Admin (FR-80 s.d. FR-85)
   - Total event, event aktif, mendatang, selesai, menunggu moderasi.
   - Jumlah Organizer dan Participant.
   - Jumlah Order dan tiket.
   - Transaksi dan pendapatan platform.
   - Filter berdasarkan periode.
   - Grafik perkembangan event, pengguna, penjualan, pendapatan.

b) Manajemen Event Global (FR-86)
   - Admin melihat dan mengelola semua event.

c) Manajemen Akun (FR-87, FR-88)
   - Admin melihat dan mengelola akun sesuai kewenangan.
   - Penangguhan event/akun menyimpan alasan dan AuditLog.

d) Moderasi Event (FR-12, FR-16)
   - Admin menyetujui, menolak, atau meminta revisi event.
   - Admin menangguhkan event dengan alasan dan audit log.

e) Paket Layanan (FR-74, FR-75, FR-76)
   - Admin membuat, mengubah, mengaktifkan, menonaktifkan, mengarsipkan paket.
   - Paket gratis dan berbayar.
   - Fitur dan batas penggunaan per paket.

f) Langganan Organizer (FR-79)
   - Admin melihat semua langganan, filter paket/status, riwayat, pembayaran.

g) Transaksi dan Pendapatan (FR-89 s.d. FR-93)
   - Admin melihat transaksi tiket dan pembayaran paket.
   - Memisahkan gross ticket sales dari platform revenue.
   - Nilai komisi sebagai snapshot transaksi.
   - Pendapatan paket dan komisi tiket ditampilkan terpisah.

h) Keluhan dan Support Center (FR-97 s.d. FR-101)
   - Admin mencari, memfilter, dan membuka laporan.
   - Admin mengatur prioritas dan status.
   - Admin membalas pelapor dan membuat catatan internal.
   - Riwayat aktivitas laporan disimpan.
   - Catatan internal tidak terlihat pelapor.

i) Pengaturan dan Audit Log (FR-102 s.d. FR-106)
   - Admin mengelola pengaturan platform yang diizinkan.
   - Perubahan komisi/biaya tercatat.
   - Tindakan administratif penting dicatat di AuditLog.
   - AuditLog tidak dapat diubah pengguna biasa.
   - Admin mencari dan memfilter audit log.

j) Profil Admin
   - Halaman profil Admin (route `/admin/profile` sudah ada di `app_routes.dart`
     tetapi BELUM ada screen-nya).
