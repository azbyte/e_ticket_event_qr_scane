A. RINGKASAN PROYEK DAN PRD
================================================================================

1. Latar Belakang
   E-Ticket Event QR Scanner adalah platform pengelolaan dan penjualan tiket acara
   dengan verifikasi QR Code. Aplikasi mendukung 4 peran: attendee (peserta),
   organizer (penyelenggara), staff (staf event), dan admin (admin platform).

2. Sumber PRD
   Dokumen utama: prd.md (versi 0.1 — draf untuk validasi)
   Status: Belum final, masih dalam tahap validasi awal
   Tim pengembang: 3 orang

3. Versi dan Platform
   - Versi: 0.1 — draf untuk validasi
   - Platform: Flutter Android dan Flutter Web
   - Backend: Node.js + Express
   - Database: PostgreSQL + Prisma ORM (via Supabase)
   - Target pasar: Indonesia

4. Fitur MVP (Minimum Viable Product)
   - Penyelenggara membuat event dan mengajukannya untuk moderasi
   - Admin dapat menyetujui atau menolak event
   - Peserta dapat mendaftar melalui browser (tanpa wajib membuat akun)
   - Sistem dapat memproses pesanan dan simulasi pembayaran
   - Tiket diterbitkan hanya setelah pembayaran terkonfirmasi
   - QR Code tiket dapat divalidasi
   - Check-in ganda dapat dicegah dalam kondisi online
   - Mode offline memiliki mekanisme sinkronisasi dan penanganan konflik
   - Peserta dapat membuat laporan kendala dan admin dapat menindaklanjutinya
   - Aplikasi dapat dijalankan pada Android dan browser

5. Indikator Keberhasilan MVP
   - Penyelenggara dapat membuat event dan mengajukannya untuk moderasi
   - Admin dapat menyetujui atau menolak event
   - Peserta dapat mendaftar melalui browser
   - Sistem dapat memproses pesanan dan simulasi pembayaran
   - Tiket diterbitkan hanya setelah pembayaran terkonfirmasi
   - QR Code tiket dapat divalidasi
   - Check-in ganda dapat dicegah dalam kondisi online
   - Peserta dapat membuat laporan kendala dan admin dapat menindaklanjutinya
   - Aplikasi dapat dijalankan pada Android dan browser

6. Struktur Pengguna (PRD section 2)
   - Peserta: dapat melihat daftar event, mendaftar tanpa akun, memilih kategori/jumlah tiket,
     mengisi data peserta, simulasi pembayaran, melihat status pesanan, mengakses e-ticket,
     menerima tiket melalui email, melaporkan kendala
   - Penyelenggara: membuat dan mengedit event, mengatur lokasi/jadwal/deskripsi,
     membuat kategori tiket, mengatur harga/kuota/periode penjualan, menayangkan event untuk
     moderasi, melihat daftar peserta dan status pembayaran, mencari/filter peserta,
     mengexpor data peserta ke CSV/Excel, mengundang/mencabut staf, melihat statistik
     penjualan dan check-in, melihat riwayat aktivitas
   - Staf Event: melakukan check-in peserta, meninjau laporan kendala peserta, mengelola
     status laporan

7. Fitur yang Diharuskan Minimum (Section 3)
   - Peserta: melihat daftar event, membuka detail event, mendaftar tanpa membuat akun,
     memasukkan email, menyelesaikan pembayara simulasi, melihat status pesanan, mengakses
     e-ticket, menerima tiket melalui email, melaporkan kendala
   - Penyelenggara: menambahkan event, event dapat disimpan dan ditampilkan kembali,
     event dapat dipilih peserta untuk registrasi, menambahkan panitia, data panitia tersimpan
   - Panitia: membuka fungsi pemindaian QR, aplikasi meminta izin kamera jika diperlukan,
     QR code pada tiket dapat dipindai, tiket divalidasi terhadap data tersimpan, tiket tidak
     valid ditolak, tiket yang telah digunakan ditolak ketika dipindai ulang, status check-in
     tersimpan

8. Analisis PRD Konflik
   - Registrasi tanpa akun (FR-04) vs pembuatan akun opsional: Registrasi tanpa akun adalah
     fitur minimum; akun opsional untuk fitur tambahan seperti riwayat pesanan
   - Mode offline vs online: Mode offline memiliki mekanisme sinkronisasi dan penanganan
     konflik, namun aplikasi didesain untuk kondisi online utama
   - Biaya layanan: belum jelas di PRD, akan ditentukan sebelum demo atau peluncuran publik

D. RANCANGAN ALUR END-TO-END
================================================================================

1. Alur Lengkap (disesuaikan dengan kriteria Section 4)
   1. Penyelenggara membuat event → event tersimpan di database sementara
   2. Penyelenggara menambahkan panitia → data panitia tersimpan
   3. Event muncul pada daftar event peserta → EventProvider memuat event
   4. Peserta mendaftar tanpa membuat akun → AuthProvider.register (tanpa role wajib)
   5. Peserta memasukkan email yang valid → InputValidator.email
   6. Peserta menyelesaikan pembayaran simulasi → PaymentProvider.simulatePayment
   7. Sistem menyimpan registrasi → Registrasi disimpan ke database sementara
   7.1. Sistem menerbitkan tiketunik → TicketModel dibuat dengan tokenunik
   7.2. Tiket dikirim ke alamat email peserta → EmailService merekam/mentransmisikan
   7.3. Tiket memuat QR code yang dapat dibaca → QrTicketDisplay menampilkan QR

   8. Panitia memindai QR pada tiket tersebut → ScannerService.validateToken
   8.1. Tiket divalidasi terhadap data registrasi → dicek di database sementara
   8.2. Hasil validasi ditampilkan dengan status jelas → status valid/invalid/gagal

   9. Tiket ditandai telah digunakan setelah check-in berhasil → CheckInModel disimpan
   9.1. Status check-in tersimpan (checked_in vs valid)

   10. Pemindaian ulang terhadap tiket yang sama ditolak → CheckInModel status
       already_checked_in atau similar; pengecekan pada database sebelum menyimpan

N. KESIMPULAN DAN LANGLANGGANG SEBELUM IMPLEMENTASI

KESIMPULAN:
Proyek Flutter E-Ticket Event QR Scanner sudah memiliki fondasi yang baik:
model data lengkap, service layer yang terdefinisi, provider stub, dan route
constant. Namun, aplikasi belum dapat dijalankan sebagaimana mestinya karena
main.dart masih template default, provider package belum terpasang, ApiClient
belum diimplementasi, dan router hanya menangani 3 route.

Pembagian tugas untuk 3 developer didasarkan pada tanggung jawab fitur:
- Developer 1: Fondasi, infrastruktur inti, dan autentikasi (pemilik file shared)
- Developer 2: Fitur peserta/attendee (event, pesanan, pembayaran, tiket)
- Developer 3: Fitur staf, organizer, dan admin (check-in, manajemen, moderasi, laporan)

Ketiga developer dapat bekerja secara paralel karena:
1. Model data sudah lengkap dan dapat digunakan oleh semua developer
2. Mock mode memungkinkan pengembangan tanpa backend
3. File shared memiliki satu pemilik (Developer 1) yang mengatur integrasi
4. Tidak ada overlap kepemilikan file antara developer

LANGLANGGANG SEBELUM IMPLEMENTASI:
1. Tim menyetujui laporan pembagian tugas ini
