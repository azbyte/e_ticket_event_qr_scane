PEMBAGIAN TUGAS PENGEMBANGAN ROLE ORGANIZER
Sumber analisis: prd.md (terutama bagian 2, 5, 8, 11, 13, 14, 15, 17, 18, dan audit bagian 20; snapshot 2026-11-05) dan source aktual di apps/lib serta backend.
Fokus tahap: Tahap 0 — Flutter UI prototype, data dummy/mock service, tanpa backend/API/database.

======================================================================
1. GAMBARAN PROYEK DAN ROLE ORGANIZER
======================================================================

Aplikasi ini adalah platform tiket acara dan pemindaian QR. Source aplikasi saat ini adalah Flutter/Dart di apps/lib. State management memakai Provider; dependency yang tampak pada apps/lib/pubspec.yaml meliputi provider dan http. Backend yang ada di workspace memakai Node.js/Express, Supabase/PostgreSQL, tetapi keberadaannya bukan persetujuan untuk mengembangkan backend pada tahap ini.

Menurut PRD, role global adalah Participant, Organizer, dan Admin. Organizer adalah pengguna global; untuk setiap event, ia memiliki keanggotaan Owner atau Staff. Owner mengelola event miliknya, sedangkan Staff hanya boleh mengakses event dan tindakan yang diberikan permission oleh Owner. Staff bukan role global. Jangan mempertahankan atau memperluas `UserRole.staff` sebagai role global tanpa keputusan produk; rekonsiliasi enum adalah isu yang perlu dikonfirmasi, bukan ruang lingkup untuk mengubah model global pada tugas ini.

Area Organizer yang direncanakan meliputi dashboard dan navigasi, event dan tiket, peserta dan order, registrasi dibantu, tim/permission, scanner/check-in, laporan/aktivitas, paket/langganan, profil, notifikasi dan bantuan. UI harus responsif Android serta Web/desktop, memiliki state loading, empty, error, success, akses ditolak, validasi form dan konfirmasi tindakan destruktif jika relevan.

2. RINGKASAN KONDISI IMPLEMENTASI ORGANIZER SAAT INI
======================================================================

Status berikut mengikuti audit kode di PRD bagian 20 dan pemeriksaan struktur source. Keberadaan halaman, route, model, atau service saja tidak membuktikan alur bisnis end-to-end.

- Sudah ada sebagian: layar dashboard, event management/form, profil Organizer, daftar peserta, pengelolaan Staff; model Event/TicketType/User, provider Event/Auth, dan service terkait. Sebagian service berkomunikasi HTTP saat MOCK_MODE=false. Itu tidak menjadikannya implementasi prototype dummy offline yang lengkap.
- Belum selesai/placeholder: tab Organizer dinyatakan placeholder; navigasi Organizer/Staff tidak lengkap; Staff dashboard adalah stub; akses Staff berbasis membership dan permission belum terbukti. Event, peserta, undangan, scanner, dan report screens tidak membuktikan keseluruhan alur, filter, hasil sukses/gagal atau persistensi lokal.
- Route map terpisah: `apps/lib/routes/app_routes.dart` mendefinisikan route, sementara `apps/lib/app_router.dart` adalah generator aktif yang tidak menangani seluruh nama/parameter route secara lengkap. Guard route sederhana bukan enforcement permission atau kepemilikan.
- Katalog publik, order, payment, ticket/QR, scanner, check-in, report, subscription dan dashboard tidak terbukti tersambung end-to-end menggunakan dummy data yang terkendali. Jangan menyatakan transaksi nyata terjadi hanya karena UI berubah.
- Backend aktual terbatas pada source auth/event/ticket/admin, middleware/model terkait, serta satu migration role/event membership. Tidak ditemukan route/service Organizer yang meliputi seluruh kebutuhan PRD. Untuk Tahap 0, backend tersebut tidak boleh dikembangkan.
- Test backend `npm test` memang belum dikonfigurasi (script gagal secara eksplisit); jangan menganggap test backend ada. Uji Flutter melalui test yang ada dan tambah test yang relevan dalam scope masing-masing.

Referensi source utama (semua path relatif terhadap root repository):
`apps/lib/app.dart`, `apps/lib/app_router.dart`, `apps/lib/routes/app_router.dart`, `apps/lib/routes/app_routes.dart`, `apps/lib/models/`, `apps/lib/providers/`, `apps/lib/services/`, `apps/lib/features/organizer/`, `apps/lib/features/scanner/`, `apps/lib/features/check_in/`, `apps/lib/features/orders/`, `apps/lib/features/payments/`, `apps/lib/features/reports/`, `apps/lib/features/tickets/`.

3. SELURUH FITUR ORGANIZER YANG DICAKUP PRD
======================================================================

Daftar ini memetakan kebutuhan frontend Organizer dari PRD bagian 2, 5, 8, 11, 12–15, 17–18, dan audit bagian 20. FR di bawah meliputi requirement UI Organizer langsung serta konteks UI yang dipengaruhi requirement tersebut. Fitur Admin/Participant yang berdiri sendiri tidak termasuk; screen publik hanya ditautkan/pratinjau jika dibutuhkan oleh alur Owner.
1. Autentikasi/konteks akun Organizer (FR-01): registrasi Organizer dengan nama, email, password, login/logout, sesi dan landing role yang benar. Pertahankan perilaku Participant/Admin; jangan menambahkan field registrasi yang tidak disebut PRD atau mengubah schema role tanpa keputusan.
2. Profil Organizer: lihat/edit informasi Organizer dan profil akun yang memang didefinisikan PRD, validasi, simpan mock, pembatalan, logout. Bedakan profil Organizer dari profil global bila kode mendefinisikannya.
3. Shell/dashboard Owner (FR-66): layout/sidebar/topbar responsif, navigasi seluruh menu Owner, event aktif, statistik event milik/aksesnya (draft, review, published, tiket, pending orders, peserta, check-in, gross sales), event terbaru, tindakan moderasi/revisi, notifikasi; bukan pendapatan platform.
4. Navigasi Staff (FR-65, 73): landing/dashboard Staff sederhana, daftar hanya event ACTIVE yang ditugaskan, jadwal/status dan permission; menu peserta/registrasi/scanner/riwayat/laporan hanya ketika diizinkan; profil/bantuan/logout; larangan menu bisnis/pengaturan Owner.
5. Event Saya dan lifecycle (FR-09): list/search/filter, create/edit/detail dan hapus bila aman; informasi dasar, deskripsi/poster, kategori event, jadwal/zona waktu, format/lokasi/link, kontak, pengaturan pendaftaran/peserta, kuota, draft, preview publik, submit review, status pending/published/revision/rejected/suspended, catatan revisi dan resubmit. Status moderasi tidak boleh diubah Owner secara manual.
6. Detail event: subnavigation Ringkasan, Informasi, Tiket, Peserta & Pesanan, Registrasi Manual, Tim, Scanner, Laporan, Aktivitas. Ringkasan menampilkan jadwal/lokasi, status, tiket, pending, peserta/check-in, grafik demo sederhana, URL/QR registrasi, salin tautan, preview publik dan tautan laporan.
7. Ticket types: CRUD aman, nama/deskripsi/harga/kuota/periode/status/batas pembelian, sold/remaining; fixture harus melindungi order historis, snapshot harga dan kuota tertahan/terjual; tidak menghapus tipe tiket yang sudah terpakai.
8. Peserta & Order (FR-67–69): daftar per-event, nama/email/order/ticket type, status order/payment/ticket/check-in dan SELF_SERVICE/ASSISTED; search nama/email/order, filter ticket/payment/check-in, detail order/peserta, ekspor CSV UI/simulasi bila hak paket/permission mengizinkan, minimisasi data sensitif. Jangan mark PAID.
9. Registrasi dibantu Owner/Staff (FR-30–35): form pemesan/kontak, ticket type/jumlah, data tiap peserta, ringkasan biaya dan konfirmasi → mock order bernomor → tampilan instruksi Virtual Account demo/reference/nominal/expiry/status sesuai data fixture bila berbayar → status tiket hanya sesuai fixture yang mengaku sudah dikonfirmasi; payment tidak dapat dipalsukan dari Organizer UI. Staff tidak boleh ubah harga/kuota; kuota/periode/limit/duplikasi divalidasi. Uji alur fixture yang setara dari segi state dengan registrasi mandiri tanpa membuat backend. Jangan menyiratkan mock mensimulasikan validasi server sungguhan.
10. Tim & undangan (FR-60–65): daftar Owner/Staff, email/status/permission/waktu bergabung; invite fixture aman dengan expiry, acceptance, permission edit dan revoke. Uji permission PRD secara terpisah dan eksplisit: `VIEW_EVENT`, `VIEW_PARTICIPANTS`, `ASSIST_REGISTRATION`, `VIEW_ORDERS`, `SCAN_TICKET`, `CHECK_IN_TICKET`, `VIEW_SCAN_HISTORY`, `VIEW_REPORTS`, `EXPORT_PARTICIPANTS`. Staff tidak mengundang/mencabut Staff atau mengubah Owner. Kanal undangan final masih keputusan terbuka; UI mock tidak boleh mengunci kebijakan permanen.
11. Scanner/Check-in (FR-50–59): mock scanner tanpa dependency scanner baru, scan fixture/entry QR, event dan ticket status checks, hasil valid/used/invalid/wrong event/cancelled/network issue, confirm check-in, riwayat pelaku/waktu, status offline belum diverifikasi server dan konflik sync ditandai untuk pemeriksaan. Staff dipisah permission SCAN_TICKET, CHECK_IN_TICKET, VIEW_SCAN_HISTORY.
12. Laporan & aktivitas (FR-70–73): total order/tiket/gross sales, biaya/komisi bila datanya tersedia, status order, peserta check-in, grafik per waktu, filter tanggal/ticket type, export sesuai paket/permission; activity log event berisi actor/action/time/event/summary untuk create/edit/review/ticket/staff/assisted registration/check-in/settings. Developer 2 memiliki model/fixture dan layar laporan/activity event; Developer 3 menyediakan pemanggilan event log dari aksi membership/invitation/permission miliknya melalui event logger API Developer 2, tanpa mengedit file log Developer 2. Pisahkan gross, fee, platform commission, package revenue dan hak Organizer; nilai tarif belum diputuskan.
13. Paket & langganan Organizer sendiri (FR-76–79): lihat plan, features/limits, start/end, status, perubahan paket dan payment history bila fixture PRD tersedia, transaksi paket/history screen bila termasuk Organizer. UI transaksi hanya representasi data demo; tidak membuat pembayaran paket. Harga/durasi/komisi belum final; jangan mengarang nilai.
14. Notifikasi, bantuan dan support Organizer (FR-95/96 dan navigasi PRD): daftar notifikasi/status baca; kontak resmi; form keluhan kategori/subjek/deskripsi/email kontak, nomor laporan, token/status/riwayat balasan aman; internal notes tidak pernah ditampilkan kepada pelapor. Developer 3 pemilik fitur ini. Jangan mengklaim live chat/AI; detail yang tidak dijelaskan perlu keputusan.
15. UI quality untuk seluruh item di atas: Android dan Flutter Web/desktop responsif; loading (tanpa aksi ganda), empty dengan next step, success, error/retry aman, access denied tanpa kebocoran, validasi form, confirmation destruktif, navigasi deep link/back yang benar, data dummy terpusat/mock terpisah dari widget, konsisten tanpa network/backend.
Tidak semua perilaku sudah dapat dipastikan dari kode. Audit PRD mencatat screen peserta/form/event/staff/dashboard ada sebagian, tetapi tidak mengonfirmasi seluruh interaksi atau fixture. Seluruh 15 kelompok di atas masuk scope kerja; masing-masing kriteria hanya boleh ditandai selesai setelah demonstrasi/test. Kebijakan yang belum diputuskan bukan alasan menghilangkan layar: bangun UI netral berbasis fixture yang tidak mengunci kebijakan bisnis dan catat keputusan yang dibutuhkan.

4. KEKURANGAN DAN KEBUTUHAN PENGEMBANGAN
======================================================================

Kategori yang sudah selesai tanpa perubahan: Tidak ada kelompok fitur Organizer yang dapat dinyatakan selesai seluruhnya berdasarkan bukti audit PRD bagian 20. File yang ada adalah bukti implementasi parsial saja. Jika developer membuktikan subalur tertentu lulus acceptance criteria di bawah melalui aplikasi/test, dokumentasikan sebagai selesai parsial/terbatas, bukan memperluas klaim ke fitur lain.

Sudah tersedia tetapi perlu diperbaiki/dilengkapi:
- Dashboard Organizer, event list/form/management, profil, attendee list dan staff management: lengkapi alur, state, permission, navigasi dan fixture fungsional.
- Model/provider/service event, order, ticket, payment, check-in, report, auth/user: audit terlebih dahulu. Gunakan pola Provider dan mock lokal; jangan mengganti pendekatan atau menganggap operasi HTTP sebagai mock.
- Shell/tab/router dan akses role: satukan pemetaan route tanpa menghapus kompatibilitas route; implementasikan owner/staff per-event sesuai PRD. Hindari perubahan model global tanpa keputusan.
- Screens scanner, report, order, payment dan ticket yang sudah ada: integrasikan sebagai tampilan operasional Organizer hanya sejauh sesuai PRD, permission dan data dummy; implementasi saat ini belum terbukti utuh.

Belum tersedia atau belum terbukti dan harus dilengkapi dari awal bila belum ada:
- Seluruh 15 kelompok fitur pada bagian 3; tidak ada yang otomatis dikecualikan hanya karena belum tampak di source.
- Detail subtab event (ringkasan, informasi/revisi, tiket, peserta/order, registrasi manual, tim, scanner, laporan, aktivitas), Owner dashboard dan Staff dashboard.
- Profile/account journey, Owner/Staff navigation, membership/permission route guard, undangan/expiry/acceptance/revoke.
- Fitur paket/langganan dan tampilan riwayat perubahan/pembayaran paket; laporan/aktivitas/export yang hak akses dan sumber fixture-nya konsisten.
- State UI responsif dan loading/empty/error/success/access-denied pada setiap layar/aksi yang relevan.

Batas arsitektur wajib: PRD bagian 15 dan 18 memerintahkan Flutter UI prototype dengan data dummy terkontrol dan mock service/repository yang terpisah dari widget, tanpa request jaringan/API, backend atau database. Seluruh fitur pada pembagian ini harus dapat didemonstrasikan tanpa server; mock boleh menggunakan memory/local fixtures, tetapi tidak boleh mengaku menyimpan transaksi sungguhan atau aman lintas pengguna/perangkat. Bagian 13.2–13.4 menjelaskan target integrasi backend berikutnya, bukan tugas saat ini. Jangan membuat endpoint, migration, tabel, konfigurasi, integrasi Supabase, atau menyalakan API. Pastikan jalur Organizer tidak memanggil HTTP walaupun mode aplikasi umum memiliki ApiClient/HTTP.

======================================================================

Gunakan 3 developer. Ketiganya mulai implementasi dalam waktu bersamaan setelah satu sesi kickoff singkat untuk menyepakati interface/file boundary; tidak ada developer yang harus menunggu fitur developer lain selesai. Developer 3 mulai dengan route table yang mendaftarkan tujuan domain menggunakan stub/temp screen atau callback sementara yang ia miliki; saat Developer 1/2 menyerahkan signature, Developer 3 mengganti stub dengan integrasi screen tanpa mengedit file mereka. Tidak ada tugas yang menunggu fitur lain selesai, hanya integrasi final yang bergantung pada kontrak stabil. File edit tiap domain eksklusif sesuai bagian 8; perubahan route/root hanya Developer 3.
